## At a glance

### Summary

The fifth SDD area pass. It states, as current truth, what a committed `*.scenario.json` and
`*.topology.json` may say, what running one guarantees under the stepped and the real clock, and
what a topology's `contractPairings` declaration means. It absorbs six RFCs (0006, three 0008-*,
0010, 0020), rewrites the area's test suites to `testing-conventions.md` §9–17 with cited ids, and
fixes the defects the extraction found in place.

### Spec implications

Creates `docs/specs/scenarios.md` (`trace: enforced`) — one page covering the scenario file, the
topology file, and stepping, because the three are one contract in practice: a scenario names a
topology, a step's meaning depends on the clock the topology's host was built with, and a pairing
declared in the topology is what makes a scenario's closed loop run. Page name recorded under `D1`.

The page cites rather than restates: `docs/specs/config-gating.md` for `[InstantiationParameter]`
decoding and inclusion gates, `docs/specs/introspection.md` for the member/contract vocabulary a
name path resolves against, `docs/specs/emission.md` for the property-vs-measuring-point split a
name path can land on, and `DALE046` (ANLZ's registry) for the wire-type analyzer. The DevHost
control API (`CTRL`), the SPA internals (Tier C), the TestKit's virtual time (`TKIT`) and block
lifecycle (`LIFE`) stay out.

### Decisions

- `D1` — **The page is `docs/specs/scenarios.md`, area code `SCEN`, and it states all three
  subjects** (scenario file, topology file, stepping) — because a step's meaning is a joint fact
  about the file and the clock, and a pairing is declared in one file and observed from the other.
  Splitting them would put a criterion's subject on one page and its condition on another.
- `D2` — **Criteria are cited from committed scenarios where the scenario is the only place the
  behaviour is observable end to end, and from unit tests everywhere else.** `spec-trace.ps1:164-172`
  already scans `*.scenario.json` for `AC-` ids in `specs`/`spec`, and `:175-194` warn-notes a test
  file that cites an id a scenario also claims with no `Cross-tier` clause. The SmokeHost's eight
  scenarios carry label strings today (`"specs": ["smoke", "hal", …]`), not ids; the pass adds ids
  **alongside** the labels rather than replacing them, so the existing filter vocabulary survives.
  (Question 3.)
- `D3` — **`Vion.Dale.DevHost.Test/` loses its whole-project exemption in
  `scripts/test-style-lint.ps1:55`; the entry narrows to the individual files `CTRL` still owns.**
  The script matches an exempt key as a repo-root-relative *prefix* (`:64`,
  `$relPath.StartsWith($_)`) and checks staleness with `Test-Path` (`:88`), so a file path is a
  valid entry under both. Files this pass authors conform to §12/§13 whatever the exemption says.
  (Question 4.)
- `D4` — **The per-project `.dale/*.schema.json` copies are `CLI`'s, not this page's.** They are
  emitted by `dale scenario schema` (`Vion.Dale.Cli/Commands/ScenarioCommand.cs:283-291`), which
  enriches the generic schema with the topology's own name-path enum
  (`ScenarioFileChecks.EnrichSchemaWithNamePaths`, `:122-189`), so they are *derived per project
  and expected to differ* — drift between them is not checkable and not a gate candidate. What IS
  this page's is the **canonical pair** and the rule that the CLI ships the canonical scenario
  schema as a build-time link (`Vion.Dale.Cli/Vion.Dale.Cli.csproj:30-31`), never a copy.
  (Question 5.)
- `D5` — **No step kind is refused for the active clock mode today, and the page states that.**
  `docs/devhost-conventions.md` § 3 states the *rule* ("a step kind that cannot behave correctly in
  the active mode must be refused … at resolve time, where it can name the offending step"); the
  code satisfied it by removing `wait` and making `advance` / `settle` / `waitUntil` **host-adaptive**
  instead (`ScenarioRunner.cs:511-541`, `:617-691`, `:869-1006`). There is no resolve-time
  clock-mode check anywhere (`grep IsStepped` returns only the adaptive branches). The page states
  the host-adaptive contract per step kind; § 3 stays where it is as the rule for the *next* step
  kind. Drift checkpoint `DC-3`.

### Error-model overview

Three refusal layers, and which one fires is itself a contract:

1. **Structural** — `ScenarioFile.Parse` / `DevTopologyFile.Parse`, host-independent, no
   configuration needed, every problem reported at once.
2. **Resolution** — `ScenarioResolver`, run-time, against the wired host's `ConfigurationOutput`;
   collected up front for the whole file before any step executes.
3. **Execution** — a step's own failure detail.

The topology file adds a fourth split of its own: `DevTopologyFile.Parse` (structure),
`DevTopologyLoader.Build` (catalog + interface compatibility + pairing structure, host-independent),
`TopologyHostCheck` / `ContractPairingTable.Build` (wire-type identity, needs introspected blocks).

### A probe that lied, and how it was caught

Setting a combobox's `input.value` from `evaluate_script` (even with the native setter plus
`input` / `change` events) moves the DOM but **not** the editor's model: the `{ } raw` view still
read `"contract": "Setpoint"` while the DOM read `IoBlock.ActiveOutput`, and the resulting `valid`
verdict was about the row that was still there. The observation was only real once the option was
clicked and the raw view agreed:

```
model step[6] = {"serviceProviderExpect":{"logicBlock":"IoBlock","contract":"ActiveOutput","equals":true,"field":"enforced"},…}
```

This is the skill's "a probe is evidence only for the shape it ran" in its browser form: the surface
a scripted write reaches is not the surface the assertion is about.
