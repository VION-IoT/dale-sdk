# Migrating to 0.12.0 — what the spec passes changed under you

`v0.12.0` is the spec-driven-development migration's release. Fourteen area passes wrote the SDK's
behaviour down as spec pages and fixed what they found on the way, so this one version carries more
behaviour change than several before it. The full list is
[`docs/release-notes/0.12.0.md`](../release-notes/0.12.0.md); this page is only the part that asks
something of you.

Four things need work rather than reading, in the order they will bite:

1. **[Before the bump](#1-before-the-bump-dual-annotated-measuring-points)** — dual-annotated
   measuring points lose the property's throttling knobs.
2. **[At the bump](#2-at-the-bump-declarations-that-stop-compiling)** — declarations that stop
   compiling, and artifacts that stop packing.
3. **[At first start](#3-at-first-start-configurations-that-stop-configuring)** — configurations
   that stop configuring, and two that start doing something they never did.
4. **[In your catch clauses](#4-in-your-catch-clauses-refusals-moved-to-the-caller)** — refusals
   moved to the caller, and one exception class that changed.

Scripts driving `dale` have their own section at the end.

---

## 1. Before the bump: dual-annotated measuring points

**This is the only item that is cheaper to do before you take the version than after.**

A `[ServiceProperty]` and a `[ServiceMeasuringPoint]` can sit on one C# property — the shape the SDK
calls common for telemetry, where the same value is live state *and* a chart. Until 0.12.0 both
streams were gated from whichever `[ServiceProperty]` the member carried, and the measuring point's
own `MinInterval`, `MinChange` and `Immediate` were read and silently ignored.

Each stream now reads its own attribute. A `[ServiceMeasuringPoint]` that declares no knobs falls to
the attribute defaults: `MinInterval = "250ms"`, no deadband, not immediate.

```csharp
// A dual-annotated member that declared nothing on the measuring point.
// Was: the chart published at 5 s, borrowed from the property.
// Is:  the chart publishes at 250 ms.
[ServiceProperty(Title = "Power", Unit = "W", MinInterval = "5s")]
[ServiceMeasuringPoint(Title = "Power", Unit = "W")]
public double Power { get; private set; }

// The fix — state the interval you were relying on.
[ServiceProperty(Title = "Power", Unit = "W", MinInterval = "5s")]
[ServiceMeasuringPoint(Title = "Power", Unit = "W", MinInterval = "5s")]
public double Power { get; private set; }
```

**A member is affected when one attribute declares a knob and the other does not** — in either
direction. Both default to `MinInterval = "250ms"`, no deadband and not immediate, so a member that
took the defaults on both sides is unmoved. The common case is a knob on the property only, and the
measuring point speeds up to 250 ms. The reverse also moves: a knob on the measuring point only,
where the stream used to run at the property's 250 ms default and now runs at its own declared
interval. Find both:

```bash
grep -rn -B6 "\[ServiceMeasuringPoint" --include=*.cs . | grep -A6 "ServiceProperty"
```

Read each hit for a knob on one attribute that the other does not repeat. The `-B6` window only
catches a `[ServiceProperty]` written **above** its measuring point; widen it if you declare them the
other way round. Counted this way in `logic-block-libraries` on 2026-09-10, 13 dual-annotated members
declare no knob on the measuring point — the number the `EMIT` pass reported, reproduced. Its
denominator is not reproducible and is left out here rather than restated.
[`examples/Vion.Examples.Emission`](../../examples/Vion.Examples.Emission)'s `SensorBlock` is the shape that was already correct — 2 s on the property, 500 ms and a deadband on
the measuring point, each now honoured as written.

Nothing breaks if you skip this; the data keeps flowing, faster. It is on this page because a rate
increase on a charted series is worth choosing rather than discovering.

## 2. At the bump: declarations that stop compiling

Each item here refuses a declaration that previously compiled and then did nothing, threw at
configuration, or shipped an artifact that could not activate. **Read the severity column first.** An
Error fails your build at the bump; a Warning does not, and the two Warnings below are both backed by
a refusal that fires later — at configuration for `DALE012`, and nowhere at all for `DALE013`, which
is advisory. If you build with warnings-as-errors this distinction does not apply to you.

| Diagnostic | Severity | Refuses | Was |
| --- | --- | --- | --- |
| `DALE005` | Error | a `[Timer]` interval that is `NaN`, infinite, longer than 4294967 s, or shorter than one clock tick (100 ns) | built, then threw at configuration |
| `DALE043` | Error | `[IncludedWhen]` on a non-logic-block type, or on any member | accepted, did nothing |
| `DALE048` | Error | a blank or whitespace `[ServiceProviderContractType]` token | reached introspection as a contract type with no name |
| `DALE041` / `DALE042` | Error | a bad `VisibleWhen` predicate on an **abstract** block | surfaced only in the consumer's build |
| `DALE020` | Error | now reads a unit off whichever emission attribute states one, so a dual-annotated member's conflict is judged where it was missed | fired off the first attribute found |
| `DALE012` | **Warning** | a base-class and a derived-class `[Timer]` resolving to one identifier | one of the two silently never ticked |
| `DALE013` | **Warning** | an `internal [PublicApi]` type with no `<summary>`; public types nested in public types | not asked |
| `DALE033` | **Warning** | now judges **every** emission attribute of a dual-annotated member, and a `[StructField]`'s `StringFormat` | judged the first attribute found |
| `DALE047` | **Warning** | a `[Command]` / `[StateUpdate]` / `[RequestResponse]` struct declared beside its contract class rather than nested in it | the generator read nothing and emitted nothing |

**`DALE012` is the one to go looking for.** It is a Warning, so a clean-ish build will scroll past it
— and the same duplicate identifier is a hard refusal at configuration
([§ 3](#3-at-first-start-configurations-that-stop-configuring)). A build that only warns here is a
block that will not start.

Two attribute placements are now compile errors, and both were always inert: `[Presentation]` is
**properties-only** and `[StructField]` is **constructor-parameters-only**. If either fails your
build, delete the declaration — restoring it somewhere else would only restore an attribute nothing
read.

**And `dale build` / `dotnet pack` refuse three artifacts** they used to produce:

- a concrete logic block missing from its plugin's `IConfigureServices` — register it, or make the
  type `abstract`;
- an `[IncludedWhen]` predicate that does not parse, or that names something the block does not
  declare as an `[InstantiationParameter]`;
- a blank or duplicated endpoint identifier.

**Only the second was already a build error.** `DALE043` judges `[IncludedWhen]`, so a library that
builds clean with the analyzer pack wired and nothing suppressed is unaffected by that one. There is
**no analyzer for registration at all**, so the first refusal is new at pack for everyone: a concrete
logic block you forgot to register builds perfectly and then fails `dale build` / `dotnet pack`,
naming the type.

**If a suppression is what got you here, read it before you widen it.** A `#pragma warning disable`
around one of these is now hiding a declaration that will fail at configuration instead
([§ 3](#3-at-first-start-configurations-that-stop-configuring)) — and it hides `DALE012` completely,
since nothing else in the build will mention it.

**Diagnostics that stopped firing** need no action, but they change what a clean build means:
`DALE001` on a contract-typed property declared on an interface, `DALE026` on a `Group` key matching
a platform `PropertyGroup` constant (which fired on every consumer since it shipped), `DALE015` on a
subsumed namespace prefix, and two of the three `DALE044`s a single non-public
`[InstantiationParameter]` used to draw. `DALE020` and `DALE033` appear in both lists and that is not
a contradiction: each stopped reading the wrong attribute and started reading the right one, so a
base-class `DALE020` and a method-parameter `[StructField]` go quiet while a dual-annotated member's
real conflict is now seen.

## 3. At first start: configurations that stop configuring

These are refusals at configuration or start, so they surface the first time a block runs — in a
DevHost session, a scenario run, or the runtime.

**A `[Timer]` the binder cannot schedule is refused, naming the method.** Six declarations that were
accepted are now refused: two timers sharing an identifier (only one ever ran, and it ran on both
intervals), an empty or whitespace identifier, an interval that is not a number, an infinite one,
one longer than a real clock can wait, and one shorter than a single clock tick — which armed a tick
chain at no delay at all.

**Three binding declarations are refused.** Each bound nothing and reported nothing before, so a
block ran with a null or a topology addressed an identifier that was never minted:

- a `[ServiceProviderContractBinding]` on a property whose type carries no
  `[ServiceProviderContractType]`;
- a `[LogicBlockInterfaceBinding]` whose `ForInterface` the annotated class or property does not
  implement;
- a `[LogicBlockInterfaceBinding]` on a non-public property.

**A second configuration of a live block throws.** Re-configuring in place used to be applied
additively, so a gate flipping closed left its member bound. The documented contract is that
changing a parameter re-activates and recycles the block, and the code now matches it. If you drive
`InitializeLogicBlock` yourself, confirm no path re-sends it to a live actor.

**A runtime write to an `[InstantiationParameter]` is refused** and answered with the unchanged
value. Tooling that wrote one was relying on undefined behaviour; the value now stays put.

**A blank or duplicated endpoint identifier fails block start**, not only the pack, naming the
declarations. A blank one addressed nothing; a duplicated one silently dropped whichever binding
bound first.

### Two members that start working

Both were silently inert and are now discovered, which means they start *doing* something on the
bump. Nothing in the SDK's own examples or in `logic-block-libraries` had either at the time of the
pass — every `[Timer]` there is a public method on a concrete block and every `[Persistent]` is
public — but a base class of your own may.

- **A private `[Timer]` on a base class now ticks.** A base class that scheduled its own cycle never
  did. Note the interaction: a base and a derived timer sharing a method name are now the duplicate
  identifier above, and are refused.
- **A private `[Persistent]` on a base class now persists.** It used to be lost on every restart,
  and starts appearing in the persisted file.

### And two that stop double-working

A **second start** or a **second stop** is now acknowledged and does nothing. A second start used to
run the hook again, republish every value and arm a second periodic-save chain that only a stop
retired — so a block started twice wrote its snapshot twice a minute for the life of the process. A
stop and a restart inside the save interval had the same shape. A **first** stop on a block that
never started is unchanged and still runs the hook.

## 4. In your catch clauses: refusals moved to the caller

The pattern across HTTP, Modbus and I/O: a call that used to be swallowed, dropped or answered with
a fabricated value now throws at the caller, synchronously, naming the parameter and the member.
Nothing that worked before throws now — but code that relied on a silent failure will hear about it.

### The one exception class that changed

**The HTTP client's own timeout ceiling now arrives as `TimeoutException`.** It used to expire as
`TaskCanceledException` while a per-request timeout expired as `TimeoutException`, so this was
invisible to a block catching only the latter — including on every request that set no per-request
timeout at all.

```csharp
// Was: this caught a per-request timeout and missed every ceiling expiry.
catch (TimeoutException ex) { … }

// Is: it catches both. The message names which bound elapsed.
// If you also had a TaskCanceledException arm to cover the ceiling, it is now dead code
// for that cause — a genuine cancellation still arrives as TaskCanceledException.
```

The other half of the same fix: a failure raised *after* the per-request bound elapsed keeps its own
class. The body read and the deserialization run outside the token, so that window is real, and a
body that would not parse now arrives as `JsonException`, a broken stream as whatever the stream
raised, and a 502 judged late as `HttpRequestException`. All three used to be reported as
`TimeoutException("Timed out after n seconds")`.

### HTTP calls that used to lose their request

Three now throw synchronously instead: a null `dispatcher`, a `timeout` outside the band the runtime
accepts, and a `SendRequest` given a null request or a null `RequestUri`. A response-bearing member
given a null success callback now schedules nothing, where it queued an action that threw a
`NullReferenceException` inside the block's actor. All eight `ILogicBlockHttpClient` members carry
`<exception cref>` tags for what they throw.

### Modbus calls that used to reach the wire

A read or write whose `quantity` or `count` exceeds the protocol's data unit is refused before the
wire with an `InvalidCountException` and an `Invalid` receipt. The limits are published as
`ModbusProtocolLimits`: 125 registers to read, 123 to write, 2000 bits to read, 1968 to write. A
`quantity` of zero is refused the same way, which is new — a `count` of zero already was. It used to
be dispatched and come back a code-less frame fault that closed the socket.

Configuration setters refuse more too — `Port` of 0, a non-positive `ConnectionTimeout` or
`DefaultOperationTimeout`, a `MaxQueuedAge` of zero or less, a `QueueOverflowPolicy` outside the
declared set, and any timeout above `ModbusTimeoutLimits.MaxTimeout` (just under 25 days).
`QueueCapacity` and `QueueOverflowPolicy` throw when changed after the queue exists; re-setting the
value already in force is still a no-op.

If your block mirrors these settings as configurable properties, give them the same bounds. The
first consumer already declares `Minimum = 1` on `Port`, and its largest read is 40 registers, so
nothing there is near a limit.

### The inbound payload guard

Every digital and analog state decode now verifies the buffer against its schema and drops the
message with a Debug log when it does not verify. Two failures disappear with it: an empty payload
used to throw out of the handler, and **a payload truncated in flight used to deliver a fabricated
value to every block bound to that contract.**

Nothing to change — every payload a HAL actually sends still passes, non-finite analog values
included. It is here because the failure it replaces was silent, so if you have a workaround
downstream that filters implausible values on a contract, this is the fix it was waiting for.

## Scripts and CI driving `dale`

The tool's invocation contract was re-cut. Nothing here needs a code change in a logic block, but a
pipeline may need one.

| If your script… | Then |
| --- | --- |
| parses `dale list`/`dale pack` `--output json` and tolerated a banner | the banner is gone; the document is the whole of standard output |
| captures a failure from standard output in **table** mode | table-mode failures now go to standard **error**. JSON mode is unchanged |
| passes `-o` to `dale scenario schema` or `scaffold` | it still works this release; the option is now `--out`/`-O`, and `-o` is a short form kept for one release |
| passes `--output json` to `dale scenario schema` | it now prints the schema. It used to write a file literally named `json` |
| runs `dale scenario validate` over a directory as a rename-catching gate | an empty directory now fails, where it reported "Validated 0 scenario file(s)" and exited 0 |
| works around `dale dev --export-config`'s exit code | drop the workaround; it exits 0 when the export was written, whatever the host's own code |
| passes `--project` to `dale build`/`dale test` | it now builds that project rather than the solution above the working directory, and an unusable path is refused rather than silently replaced |
| runs `dale upload` in a directory holding sibling packages | it matches by exact package id, and reports finding none rather than uploading the newest |
| logs in to one environment and uploads to another | that is now refused by name, with the command that fixes it |
| prompts interactively under `--output json` | `dale login` and `dale config set-integrator` refuse instead, naming `--integrator-id` |
| greps captured output for `✓` or `—` | the tool writes UTF-8 now, so they survive redirection |

**One new line you will see and should not script against.** When the running `dale` is older than
the `Vion.Dale.Sdk` a project references, the tool prints a caution naming both versions and the
`dotnet tool update -g Vion.Dale.Cli --version <sdk>` line that fixes it. It is a warning, not part
of any document, so `--output json` is byte-identical. Only the older direction warns — a newer tool
against a pinned older SDK is a deliberate pin, and a `0.0.0` local or CI build is silent.

## If you drive the DevHost

The control API's refusals are in [the release notes](../release-notes/0.12.0.md#the-devhost-control-api);
the short version is that five routes that answered `200` on a request nothing could serve now
answer `400` or `404`, so **a client that checked only `response.ok` was previously being told a
poke landed when nothing received it.**

Two removals need a code change if you use them:

- **`DevConfigurationBuilder.ShareContract` is gone.** `PairContracts` retired it. They are not the
  same capability — pairing is a wire between two endpoints, sharing was a fan-in to one — so this
  is a re-model, not a rename. Topology files carry `contractPairings` and never had a
  shared-endpoint form.
- **`ScenarioRunOptions.WriteAcknowledgementWindow` is gone.** The host's own window is the only
  number now, so a host built with a short window can no longer report a refused write as a
  succeeded step. Where you set budgets deliberately,
  `DevHostBuilder.WithSafetyBudgets(DevHostBudgets)` is the one knob: the write-acknowledgement
  window, the start-acknowledgement backstop, the stop-sequence budget and the quiescence ceiling,
  which were private constants.

## If you host plugins

One resolution rule changed, and it changed towards isolation. A plugin binding to an assembly in
its own directory that is **not** marked `[DaleSharedAssembly]` now gets a copy private to that
plugin, even when a shared instance with the same simple name already exists. Eager loading over a
missing directory completes without loading anything, as context construction already did, and a
marked assembly the plugin's context has already loaded is registered as the shared instance for its
simple name.
