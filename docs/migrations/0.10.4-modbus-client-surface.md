# Migrating to 0.10.4 — the Modbus client surface

`v0.10.4` reshapes both Modbus clients: every callback now carries a receipt, both clients share one
`IModbusClient` base, and the TCP client gained a link policy that reconnects and backs off on its own.
The compile break is mechanical; the behaviour changes are not, and the second half of this page is the
part worth reading twice.

Worked examples of everything below: [`examples/Vion.Examples.ModbusTcp`](../../examples/Vion.Examples.ModbusTcp)
(TCP, with a simulated device and two committed scenarios) and
[`examples/Vion.Examples.ModbusRtu`](../../examples/Vion.Examples.ModbusRtu) (RTU).

## The compile break, and the recipe

Every read and write on `ILogicBlockModbusTcpClient` and `IModbusRtu` carries a
`ModbusReceipt` in both callbacks. There are no compatibility overloads — the old shapes are gone.

| Was | Is |
| --- | --- |
| `Action<T> successCallback` | `Action<T, ModbusReceipt> successCallback` |
| `Action successCallback` (writes) | `Action<ModbusReceipt>? successCallback` |
| `Action<Exception>? errorCallback` | `Action<Exception, ModbusReceipt>? errorCallback` |

So: **add `, ModbusReceipt _` to each handler method, and `, _` to each lambda.** Where you want the
receipt, name it instead of discarding it.

```csharp
// before
Modbus.ReadInputRegistersAsFloat(UnitId, 0, 3, values => Voltage = values[0], OnError);
private void OnError(Exception ex) { … }

// after
Modbus.ReadInputRegistersAsFloat(UnitId, 0, 3, this, (values, _) => Voltage = values[0], OnError);
private void OnError(Exception ex, ModbusReceipt receipt) { LastError = $"{receipt.Outcome}: {ex.Message}"; }
```

`Disconnect` is unchanged.

### RTU also takes a dispatcher

`IModbusRtu` is now `IModbusClient`, so every RTU call takes an `IActorDispatcher` before the callbacks
— pass `this` from inside a logic block, exactly as Modbus TCP always has. That is the extra `this,` in
the example above.

### RTU test gotcha: flush after every `Simulate*`

**This one compiles and then quietly fails.** RTU callbacks now travel the dispatcher, so a response
simulated by the RTU TestKit is queued rather than applied inline. Add `FlushPendingActions()` after
every `SimulateReadResponse` / `SimulateWriteResponse` / `Simulate*Error` before asserting:

```csharp
_sut.Modbus.SimulateReadResponse(ctx, ModbusResponseBuilder.FromFloats(230.5f), 0);
ctx.FlushPendingActions();

Assert.Equal(230.5f, _sut.VoltageL1, 0.01f);
```

Without it the assertion simply does not see the value. Two other RTU consequences of the same change:
validation errors are asynchronous now (they arrive at the error callback rather than throwing), and the
operation timeout starts when the handler publishes the request, not when you call it.

## What you get for it

`ModbusReceipt` (`ReceivedAt`, `ReceivedTimestamp`, `RoundTrip`, `QueuedWait`, `Outcome`) reports what
the callback itself cannot measure: the instants are taken before the callback reaches the block's
mailbox, so they date the transaction rather than the block's own backlog.

`IModbusClient.Link` accumulates those receipts into a `ModbusLinkSummary` — state, last contact,
per-outcome counters, round-trip and queued-wait statistics, queue depth. `ILogicBlockModbusTcpClient`
adds `Connection` (a `ModbusTcpConnectionSummary`: connect attempts, failures, current backoff, next
attempt). **Both are flat readonly record structs of service-property-legal types, so a block can
publish one whole:**

```csharp
[ServiceProperty(Title = "Link")]
[Presentation(Group = PropertyGroup.Diagnostics)]
public ModbusLinkSummary Link { get; private set; }
```

…assigned from `_client.Link` on a timer or inside a callback. Most hand-rolled transaction/error/latency
counters can be deleted outright; both Modbus examples did exactly that.

A block's headline status is worth deriving from the same place. `Vion.Examples.ModbusTcp` folds
`Link.State` and `Connection.State` into one status enum in the one method that republishes both, with
`BackingOff` outranking `Faulted` — so the pill can never drift from what the client thinks, and a local
failure that never reached the device (a rejected quantity, an unparseable value) cannot colour it. Those
belong in the error strings, where `$"{receipt.Outcome}: {message}"` keeps a backlog from reading as a
device fault.

`ModbusOutcome` classifies every ending: `Success`, `DeviceError`, `Timeout`, `TransportError`,
`ProtocolError`, `BackedOff`, `Expired`, `Dropped`, `Invalid`, `Cancelled`. Only the ones that reached
the wire move `Link.State` (`Unknown` / `Online` / `Faulted`) — a congested client stays distinguishable
from a broken device. New exceptions to expect: `RequestExpiredException` (Core) and
`LinkBackoffException` (`Modbus.Tcp.Client.Request`); `RequestDroppedException` now carries a `Reason`.

## Behaviour that changed without you asking

1. **`MaxQueuedAge` defaults to 30 s.** A request that has waited longer than that is not sent; it ends
   `Expired`. Set it near your poll interval so a backlog sheds stale reads instead of replaying them, or
   `null` to switch the check off.
2. **A wire fault closes the socket; the next request reconnects.** No block-side reconnect logic needed
   — and any you already have is now redundant.
3. **From the second consecutive failed connect the TCP client backs off**, 1 s doubling to 30 s
   (`ConnectBackoff` / `ConnectBackoffMax`). Requests during a backoff fail fast with `Outcome.BackedOff`
   rather than waiting out a connect timeout. There is no off switch: setting
   `ConnectBackoffMax = ConnectBackoff` makes the wait a constant, which is the floor.
4. **A *changed* `IpAddress` or `Port`, or `IsEnabled` going `false → true`, ends the backoff at once**,
   so an operator's correction applies on the next request. Setting an **unchanged** IP or port is a
   no-op — re-applying a whole configuration on every edit no longer drops a healthy socket. If your
   block wraps its assignments in a disable/re-enable cycle, drop it: re-enabling deliberately cancels a
   backoff, so the cycle hides the policy from you.
5. **Still no automatic request retries.** The client reconnects; it does not resend.

While you are there: the client's settings are `TimeSpan`s and its `MaxQueuedAge` is nullable. A block
that mirrors them as millisecond `int`s takes on a unit, and a `0 = off` translation the SDK does not ask
for. `Vion.Examples.ModbusTcp` carries them as two `[StructField]`-annotated `readonly record struct`s
instead — the shape the SDK's first consumer arrived at independently, one property and one reconfigure
chokepoint — which renders as duration controls and keeps `null` meaning `null`. (Modbus RTU has no
endpoint to configure: its binding resolves through a service-provider contract.)

`Vion.Dale.Sdk.Modbus.Core` is now shared by both transports and carries the client contract and the
diagnostics types, so it pulls in more than it used to. Referencing `Vion.Dale.Sdk.Modbus.Tcp` or
`.Rtu` brings it along as before.

**0.10.5: presentation only.** No API or behaviour change, nothing to migrate. Both summaries gained
`[StructField]` titles and descriptions and the three diagnostics enums gained `[EnumLabel]` +
`[Severity]`, so publishing `Link` or `Connection` whole now arrives labelled, and `Link.State` can be a
`StatusIndicator` pill that colours itself. If you are already on 0.10.4 you get all of it by bumping.

## Seeing it work

`pwsh scripts/smoke-modbus.ps1` boots the TCP example's DevHost against a real client/server pair on
`127.0.0.1:15020` and drives the whole policy — fault, backoff, correction, peer drop, unattended
recovery — through the committed scenarios. The example README's *"Watch the link policy"* tour is the
same thing by hand, in about a minute.
