# DevHost smoke test

Two tiers. Tier 1 is the fast headless gate (run it always); Tier 2 drives the actual browser UI (run it when changes touch the web UI / SignalR, or for full confidence). Together they cover the whole DevHost.

## Tier 1 — headless / HTTP+runtime (fast, CI)

```bash
dotnet test Vion.Dale.DevHost.Test/Vion.Dale.DevHost.Test.csproj --filter "TestCategory=Smoke" --nologo
```

Expect **every test green** — the count grows with the fixture, so a number here is stale by the next change; zero failures is the expectation. ~4 s of test execution, but **~25 s cold wall**: `dotnet test` rebuilds and runs an up-to-date check across the dependency graph, and that build tax (not the tests) dominates. For repeat runs in the same session, build once then append **`--no-build`** → ~5 s. This boots real web hosts (Kestrel + the full API/SignalR pipeline + a wired logic-block network) and sweeps the assembled surface over HTTP:

- **core sweep** (`DevHostSmokeShould`): boot/introspection (`/api/configuration`, `/api/logicblocks`), state read, **writable set + read-back**, **read-only write rejected with 400** (not a silent 200), **`stepped:true`**, a **scenario run to `succeeded`**, **manual virtual-clock advance** firing a `[Timer]`, a **HAL-input scenario** (`serviceProviderSet` + `waitUntil` → the mocked input reaches the block), and a **HAL-output scenario** (`advance` fires the `IoBlock`'s timer to mirror inputs onto its outputs, then `serviceProviderExpect` ASSERTs those outputs — the full mocked-input → block → mocked-output loop) that also boots the SmokeHost's `IoBlock`;
- **struct contract** (`ServiceProviderStructContractShould`): `serviceProviderSet` drives a third-party-shaped value contract whose payload is a multi-field struct with a 1-level nested struct + an enum into `GridBlock`, which surfaces every field (incl. the nested ones) — the RFC 0010 / DF-27 struct unblock, the non-HAL case end to end;
- **multi-field output assert** (`ServiceProviderExpectStepShould`): the outbound half of the same shape. `GridBlock` mirrors the demand onto its `GridSetpoint` contract, whose command is multi-field, and `serviceProviderExpect` asserts it one scalar at a time with **`field`** — including a nested one (`limits.activePowerW`) — leaving the publish-time `issuedAt` stamp unasserted. A second Smoke case pins the same list **over HTTP**, where the SPA editor reads it: `scenarioOutputFields` is a literal in C#, the CLI validator and the page's JS, and nothing else checks the three agree. Its sibling non-Smoke cases pin the guard: a whole multi-field command, a never-written contract, and a field the command did not carry each **fail** rather than let `notEquals` report satisfied having compared nothing;
- **output confirmations** (`ServiceProviderSetStepShould`, VION-131): the drive half of an *output*. `DigitalOutputHandler` / `AnalogOutputHandler` declare an `Inbound` (`DigitalOutputChanged` / `AnalogOutputChanged`), so `serviceProviderSet` delivers the confirmation a provider would send back and the block's `OutputChanged` fires — dead in every DevHost bench until now. The Smoke case drives a truthful confirmation, then a **wrong** one (commanded true, confirmed false) and watches `IoBlock.ConfirmationMismatch` rise, and ends with a `serviceProviderExpect` proving the confirmation never leaked into the output cache. Its siblings pin the re-keyed gate: the drive resolves on the *declared inbound*, not on `Consumers` (checked explicitly, so a fixture that stopped classifying as an output can't make it vacuous), and a contract whose handler declares no inbound — `GridBlock.Setpoint` — is refused at resolve time. The committed **`output-confirmation`** scenario runs the same loop end to end;
- **provider faces** (VION-131 slice 2): the inverted side of the HAL contracts. `Vion.Dale.Sdk.DigitalIo` / `.AnalogIo` ship four provider trios — `IDigitalOutputProvider` (`SetReceived` / `Confirm`), `IDigitalInputProvider` (`Drive`) and the `double` twins — each declared `DevelopmentOnly = true`, which reaches introspection as a `developmentOnly` annotation on the contract. The SmokeHost's **`DeviceSimBlock`** binds all four: a scenario drives `SetDigitalOutput` *into* the provider face (legal because the provider handler declares that inbound), the block confirms back and drives its feedback contact, and both outbounds are asserted with `serviceProviderExpect`. The committed **`provider-faces`** scenario runs that loop, then switches the block's take-up knob off and proves an ignored command changes nothing — non-take-up as block behaviour, not host magic;
- **contract pairing** (`ContractPairingShould`, VION-131 slices 3-4): a topology can declare two service-provider contract endpoints ONE WIRE (`contractPairings`, or `DevConfigurationBuilder.PairContracts`), and the stand-in's `Capture` re-drives the captured value onto the peer endpoint — the peer delivers it through its ordinary drive path, so no new message type and no transformation exist. The Smoke case closes the whole loop on the fixture's new **`IdealIoBlock`** (the reference "ideal I/O module" recipe): its knob drives a paired `IDigitalInput`, `IoBlock`'s `[Timer(1)]` commands the paired `IDigitalOutput`, the provider face observes `SetReceived` and confirms, and `IoBlock.ConfirmedActive` lights up — all inside one `advance`, so the loop is deterministic. Its siblings pin the refusals (a pairing with no type-identical direction fails the host start naming **both declared wire types**; an unknown contract, coinciding endpoints and a pair declared twice are refused at topology load), the resolve-time **warning** when a `serviceProviderSet` targets an inbound a pairing also feeds (legal, last write wins — the run still succeeds), and that `serviceProviderExpect` still reads a paired output's command (the cache is written before the forward). `ServiceProviderContractHandlerShould` pins the **default**: an unpaired capture forwards nothing, and the drive path never consults the pairing table. Slice 4 added the **Save/validate** half: a running host hands its introspection to the topology store, so `PUT /api/topologies/{id}` and `POST /api/topologies/validate` refuse a type-mismatched pairing with the same named-types message (and write nothing), while an unpaired topology still saves byte-identically even after an editor added and removed a pairing, and a paired one keeps its entries through an unrelated edit. The committed **`paired-loop`** scenario runs the same loop on the committed `paired` topology;
- **bidirectional contract** (`ServiceProviderExpectStepShould`, VION-129): `PlantBlock.Control` carries BOTH wire directions under ONE contract identifier (`[ScenarioWire(Inbound = ..., Outbound = ...)]`, no `Consumers`, so it classifies as an *input*) and is driven **and** asserted in a single scenario — the PPC shape the old binary direction gate refused before any read. The test checks the classification explicitly, so a fixture that quietly became an output can't make it vacuous;
- **state replay** (`HeadlessControlShould`, VION-131 slice 4): `PublishAllStates` — what the SignalR hub sends a browser on connect — asks **every discovered stand-in**, not the four HAL handlers by name, so a late subscriber is primed with a non-HAL contract's state (the test drives `GridBlock.Demand` and watches it replay). That was the last fragment of hardcoded contract support (RFC 0010 / RFC 0020 §7);
- **lifecycle + step types**: recycle-on-run (`RecycleOnRunShould`), explicit topology switch (`TopologyFilesShould`), host reset/recycle (`RunControlShould`), the deterministic `waitUntil` path (`ScenarioSteppingShould`), and the **domain stop sequence on recycle** (`TeardownStopSequenceShould` — a real reset over `/api/control/reset` must run `LogicBlockBase.Stopping()` on the outgoing generation).

Between them the smoke exercises every important scenario step type (`set` / `advance` / `settle` / `expect` / `waitUntil` / `serviceProviderSet` / `serviceProviderExpect`; only the discouraged non-deterministic `wait` is omitted).

It does **not** drive the SPA web UI (the host *serves* it but the headless test never loads the page or runs its JS). A green Tier 1 is not proof the UI works — that's Tier 2.

**If it fails:** read the failed assertion and, for a scenario failure, the printed run-report JSON — `validationErrors` (name paths are case-sensitive: `counter` ≠ `Counter`) and each step's `detail` pinpoint it. Narrow with `--filter "FullyQualifiedName~DevHostSmoke"` (core) vs `~RecycleOnRun` / `~SupervisedRunner` (lifecycle). For per-feature depth, drop the filter and run the whole `Vion.Dale.DevHost.Test` project.

## Tier 2 — live UI on the SmokeHost (chrome-devtools)

`Vion.Dale.DevHost.SmokeHost` is a committed, project-referencing fixture (synthetic blocks covering every DevHost feature: value shapes, presentation groups, read-only members, a timer, HAL contracts with drivable output confirmations, the four provider faces, an ideal-I/O module for paired benches, a bidirectional contract, inter-block wiring; four topologies; eight scenarios). It boots a **real** DevHost server against local source — **no temp project-ref switching**. A subagent can run this after DevHost work.

1. **Boot it** (stepped + headless), with the working directory set to the project dir (folder-driven discovery is cwd-relative):

   ```powershell
   $dir = "$(git rev-parse --show-toplevel)\Vion.Dale.DevHost.SmokeHost"
   dotnet build $dir --nologo
   $env:DALE_DEVHOST_STEPPED = "1"; $env:DALE_DEVHOST_NO_BROWSER = "1"
   Start-Process dotnet -ArgumentList "$dir\bin\Debug\net10.0\Vion.Dale.DevHost.SmokeHost.dll" -WorkingDirectory $dir -WindowStyle Hidden
   ```

   Poll `http://localhost:5000/api/control/status` until it responds (`stepped:true`). (Boot-to-ready is ~1 s — the ~50 s is the `dotnet build`. If the solution is already built, e.g. you just ran Tier 1 or `dotnet build`, skip `dotnet build $dir` and boot the existing DLL.)

2. **Drive the UI** with the chrome-devtools MCP. If no page is connected, open one (`new_page`); if you genuinely can't drive a browser, fall back to Tier 1 + API checks against `localhost:5000` and say so. Navigate to `http://localhost:5000` and reload with `ignoreCache` (dodges stale assets). A leftover route or pins from a previous session are harmless — reload to the root, or use an isolated context / clear localStorage for a clean view. Then verify:
   - The page loads and the Explorer lists the seven blocks (Showcase, IO Device, Device Sim, Grid Demand, Plant Control, Signal Source, Signal Sink). Device Sim carries four contracts in the wiring panel — the provider faces `Schütz` / `Rückmeldung` / `Stellwert` / `Istwert`. Grid Demand carries two contracts in the wiring panel — the inbound `Demand` and the outbound `Setpoint`; Plant Control carries one, `Control`, which is *both* (VION-129).
   - Step the clock first (`+10s`) so the live metrics populate, then confirm the value shapes render on `ShowcaseBlock` — status pill (enum), struct, **sparkline** (array; empty until stepped), duration, a bounded number field (writable double, min/max — `uiHint=slider` is advisory, the control is a number field, not a range slider), bool toggle. Also expand a member's docs and confirm the emission chips render: `Sollwert` shows **throttle 1s · Δ0.1** + **persistent**, and `Cycles` shows **immediate**.
   - **Conditional visibility (`VisibleWhen`).** First run the vendored conformance vector through the SPA's evaluator — `window.__predicates.runVectorSelfTest(await (await fetch('/predicate-conformance.json')).json())` must return `passed: true` with an empty `failures` array (the wwwroot `predicate-conformance.json` has no other runner — Tier 1 only checks it is served 200). Then exercise the live hide/show on `ShowcaseBlock`: the `configuration` group shows `DirectMeasurement` (a bool toggle) plus `PrimaryCurrentToWriteA` / `SecondaryCurrentToWriteA` (the two CT-ratio inputs, `[Presentation(VisibleWhen = "DirectMeasurement == false")]`). With `DirectMeasurement` **off** both CT rows render at full opacity; toggle it **on** and both dim to the `hidden-importance` treatment (opacity `0.45`) within a beat (the SignalR echo), and toggling **off** restores them — reactive, no reload. (Assert via the item elements' class list: `document.getElementById('item-<svcId>-PrimaryCurrentToWriteA').classList.contains('hidden-importance')` flips with the toggle. The DevHost dims a hidden row — the dashboard is the surface that removes it.)
   - **Struct-field presentation.** `ShowcaseBlock.CurrentLink` / `DesiredLink` (the `LinkProfile` struct) is the fixture: **view** it and each row must read as its `[StructField]` Title with the camelCase wire key beside it (`Round trip (last) roundTrip`). `state` is the enum field and the VION-105 check: its schema title is its *type* name, so its authored title, value labels and severities ride `presentation.fields.state` instead — the row must read **`State state`** (not the bare key, and not `Mood`), its value must read **`Ruhig (Calm)`** (the `[EnumLabel]`, not the bare member name), and it must render as a **status pill** coloured by the member's `[Severity]` — `Calm` success, `Busy` warning, `Overloaded` error. `roundTrip` reads `910 ms`, never `PT0.91S` or `00:00:00`; `lastContactAt` reads as a date. **`{ } edit`** it and the form shows the same labels, the `state` picker offers `Ruhig (Calm)` / `Beschäftigt (Busy)` / `Überlastet (Overloaded)` with the drafted member's severity pill beside it, an `ipv4` hint on `address`, and a duration box that takes `750ms` / `1.5s` / `PT3S` / `00:00:03` alike — the normalised wire form and its humanized reading appear beside the box, and Set value writes the ISO form. Descriptions are deliberately **not** rendered inline in either surface; they live in the `▸ docs & schema` JSON.
   - Pin a member in a block (the pin control) → it appears in the watch panel; unpin → it's removed.
   - Open the **`showcase-tour`** scenario in the Player and click **Run** → green (stepped, so near-instant). Open **`io-control`** and Run → green (it drives the digital + analog HAL inputs, the block observes them, and after an `advance` it asserts the mirrored digital + analog HAL outputs — the full input → block → output loop). Moving between scenarios is the Player's scenario switching.
   - **The `serviceProviderExpect` field selector — Tier 1 cannot reach this, only the page's JS can.** Open **`grid-demand`** and Run → green; its last four steps assert the multi-field `GridBlock.Setpoint` command field by field. Then edit it: a `serviceProviderExpect` row carries a **`field`** combobox between the contract picker and `equals`. Pick `GridBlock.Setpoint` and the box offers exactly `enforced`, `scope`, `limits.activePowerW`, `limits.reactivePowerVar`, `issuedAt` — the command's addressable leaves, read from the contract's `scenarioOutputFields` annotation. **Clear the box** and the row shows an inline error naming those fields (a whole command is not comparable); type a misspelling and it names the field that does not exist; pick a single-value HAL output like `IoBlock.ActiveOutput` and offering a field is refused instead. Each of those is the client mirror of the resolver's check, so a green row here means the same row saves and runs.
   - **Output confirmations (VION-131).** Open **`output-confirmation`** and Run → green: after the `[Timer(1)]` commands both outputs, it drives the provider's confirmation back onto `IoBlock.ActiveOutput` / `EchoOutput` and the block's `ConfirmedActive` / `ConfirmedEcho` follow, then it confirms `false` on an output commanded `true` and `ConfirmationMismatch` goes true (all three are in the scenario's `watch`, so the panel shows them move). In the editor, pick `IoBlock.ActiveOutput` on a `serviceProviderSet` row — it saves and runs, with a **bool** value control, where before the row was refused as an output; pick `GridBlock.Setpoint` on the same row and an inline error says it cannot be driven and names `serviceProviderExpect` instead. That error is the client mirror of the resolver's re-keyed gate.
   - **Provider faces (VION-131).** Open **`provider-faces`** and Run → green: it commands the `DeviceSimBlock`'s `ContactorProvider` closed, the block's `Applied` and `ConfirmationCount` move (both are in the scenario's `watch`), and the confirmation plus the driven `Rückmeldung` contact are asserted back. Then `TakesUpCommands` goes false and the same command changes nothing. In the editor, pick `DeviceSimBlock.ContactorProvider` on a `serviceProviderSet` row — it saves and runs (the provider handler declares `SetDigitalOutput` as its inbound); pick `DeviceSimBlock.FeedbackProvider` on the same row and it is refused, because a provider-side input is one-way and declares no inbound. That asymmetry is the whole point of the provider trios and is only visible here.
   - **The bidirectional contract (VION-129).** Open **`plant-control`** and Run → green: it drives `PlantBlock.Control` with `serviceProviderSet` and, after an `advance`, asserts the measurement the block published back **on the same contract identifier** with `serviceProviderExpect` + `field`. In the editor, pick `PlantBlock.Control` on a `serviceProviderExpect` row and the `field` box offers `valid`, `timestamp`, `activePowerKw`, `reactivePowerKvar` — and, unlike an inbound-only contract, the row now saves and runs instead of failing validation. Pick it on a `serviceProviderSet` row too: the same contract drives, with no field.
   - **Contract pairing (VION-131).** Open **`paired-loop`** and Run → the host recycles onto the `paired` topology and the run goes green: the `IdealIo` knob closes the simulated contact, the paired digital input carries it to `IoBlock`, `IoBlock`'s timer commands the paired digital output, and the ideal module's confirmation lands on `IoBlock.ConfirmedActive` — all four are in the scenario's `watch`, so the panel shows the loop close. With the host on `paired`, the Explorer lists two blocks (IO Device, Ideal I/O); poke **`Eingang geschlossen`** on Ideal I/O and step the clock, and `IoBlock`'s `Freigegeben` / `Aktiv bestätigt` follow with no scenario running — the interactive half of a paired bench (this is the only place that is visible). Switch back to `default` afterwards.
   - **Pairings in the wiring panel, and editing them.** Still on `paired`: each block's **wiring** panel counts its pairings in the summary and draws them as their own badge kind beside the interface links, with the DIRECTION the host actually materialised — `IoBlock` reads `paired ⇄ IdealIo ActiveOutput ↔ OutputChannel` (command out, confirmation back) and `paired ← IdealIo EnableInput ↔ InputChannel` (one-way: an input writes nothing), and `IdealIo` mirrors them (`⇄`, `→`). The same fact repeats on each contract row (`paired ⇄ IdealIo.OutputChannel`). Check both themes — the badge is a dashed info-accent pill. Then **`⛁ topology` → Manage / edit… → paired → ✎ edit**: the form has a **contract pairings** section listing the two entries with a ✕ each, and a two-combobox picker whose rows show every endpoint with its contract type (`IdealIo.OutputChannel · DigitalOutputProvider`). Pair a MISMATCHED couple — `IoBlock.EchoOutput ⇄ IdealIo.InputChannel` — and **validate**: one error row naming **both** declared wire types (`SetAnalogOutput` … `DigitalInputChanged`), which is the wire-type identity rule (RFC 0020 §4.3) refusing at Save/validate rather than at the next host start. Remove that row, validate again → green **valid** pill. **Cancel** (do not save — a save would rewrite the committed fixture's `contractMappings`). On `default` (unpaired) the wiring summaries must carry no pairing count and no badges at all.
   - Switch topology from **`⛁ topology`** to `minimal` → the host recycles and the header shows the new topology. (Equivalently, open **`minimal-subset`** and Run → recycle-on-run onto `minimal` through the Player.)
   - **Author a topology (RFC 0013 editor):** ⌘K → **new topology** (or the topology panel's **+ new**) → add `SignalSourceBlock` (name `src`) + `SignalSinkBlock` (name `sink`) → **⚡ AutoConnect** wires `src.ISignalSource → sink.ISignalSink` and the residue clears → set id `rig` → **validate** (green) → **save & switch** → the host recycles onto `rig` and the chip shows it. Confirms the catalog endpoint (`/api/logic-block-definitions`), the client matching/AutoConnect/residue, and the save→validate→switch round-trip. Tear down: delete the authored `Vion.Dale.DevHost.SmokeHost/topologies/rig.topology.json`.
   - **Author a scenario (RFC 0014 editor):** Verify → **＋ new** (or ⌘K → **new scenario** / `Shift+S`) → the scenario editor opens (`scenarioScreen='editor'`) → set id `rig` → **SETUP**: `+ add setup` a row, kind `set` (the setup kind dropdown offers ONLY `set`/`serviceProviderSet`), pick a **writable** property (e.g. `ShowcaseBlock.Setpoint`; read-only `Cycles` is absent), the value editor switches to the property's type (number) → enter `42` → **STEPS**: `+ add steps` a row, change kind to `expect` (the steps dropdown has all seven kinds), pick `ShowcaseBlock.Setpoint` → **apply setup** then **use current** fills `equals` with the live `42` → **validate** (no errors) → **save & run** → the run reaches **succeeded** (the `expect` step holds). Confirms the `scenario-forms.js` pickers/value-editor/validation, the writable-filter + setup-only restriction, the use-current capture, and the PUT-save → apply-run round-trip. Also worth a poke: the **`{ } raw`** tab round-trips the draft, and **WatchPanel** pins reorder (↑/↓). Tear down: delete the authored `Vion.Dale.DevHost.SmokeHost/scenarios/rig.scenario.json`.
   - **Golden regression — author a *known* scenario/topology and diff against the committed golden (the regression guard for the editor features).** Two committed fixtures hold the "known good" the editors must reproduce: `Vion.Dale.DevHost.Test/Golden/feature-tour.scenario.json` (all seven step kinds · the value-editor types — number, string, bool, nullable-number, struct, enum · a struct-field `expect` · a HAL round-trip) and `feature-rig.topology.json` (5 blocks · an interface wire · 5 completed contractMappings). Their **automated** counterpart is the Tier-1 `GoldenRegressionShould` (round-trips + runs the scenario golden to `succeeded`; PUTs the topology golden with `contractMappings:[]` and asserts decision-4 repopulates exactly the golden's 5) — so CI already guards the save/run shape. Live, spot-check the **editor authoring** unit tests can't reach: author the scenario from the golden recipe — struct `set` `ShowcaseBlock.HomePosition` (two `x`/`y` inputs) · enum `set` `PreferredMood` (dropdown) · an `expect` on the struct field `HomePosition.x` · a `serviceProviderSet`/`serviceProviderExpect` HAL pair — then **save & run** → **succeeded**, and confirm the saved `…/scenarios/feature-tour.scenario.json` diffs clean (logically) against the golden. The struct-field `expect` is load-bearing: its path uses the schema's **camelCase** wire key (`HomePosition.x`), resolved **case-insensitively** at runtime (`ScenarioRunner.ExtractField`) — if that regresses to PascalCase-only, this golden's run fails. Tear down the authored file.
   - **Editor consistency:** the scenario editor (RFC 0014) and the topology editor (RFC 0013) share their chrome — both headers are **`← back` · a `mono` "… editor" title · `form`/`{ } raw` tabs · `✕`**, and both footers end **`cancel` · `save` · `save & {run,switch}`** (with a `validate` + green `valid` pill on the left). If you touch one editor's header or footer, keep the other in lockstep.

3. **Tear down**: stop the process —
   ```powershell
   Get-NetTCPConnection -LocalPort 5000 -State Listen -EA SilentlyContinue | ForEach-Object { Stop-Process -Id $_.OwningProcess -Force -EA SilentlyContinue }
   ```

## CI

The Tier-1 `Smoke` tests run in the normal `dotnet test` pass, so this is also the regression gate for the read-only-write rejection, recycle-on-run, and no-`force` behaviors. The SmokeHost is built by the solution (a compile guard); its live behavior is Tier 2. A pipeline can run just the fast headless smoke with the `--filter "TestCategory=Smoke"` above.
